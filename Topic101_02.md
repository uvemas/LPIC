### Introduction
### BIOS or UEFI

Ambos son firmware que sirve para arrancar la máquina, pero funcionan de manera diferente.

El MBR son *los primeros 512 bytes del dispositivo de almacenamiento* que se usa para arrancar:
 
 - los primeros 440 bytes contienen el bootstrap, o sea, la primera etapa del bootloader
 - el resto contienen la tabla de particiones del dispositivo

 Un dispositivo de almacenamiento con MBR se dice que usa el esquema de particiones DOS.

La BIOS reside en un chip de memoria no volátil soldado a la placa base. Al arrancar el ordenador con BIOS:

1) la BIOS ejecuta el proceso POST (power-on self-test) para detectar errores graves de hardware
2) la BIOS activa el monitor, el teclado y el disco de arranque
3) la BIOS carga/ejecuta el bootstrap (es la única parte del disco de arranque a la que tiene acceso)
4) el bootstrap carga/ejecuta la segunda etapa del bootloader, pasándole parámetros si es necesario. La segunda etapa es la que presenta las opciones de arranque y carga el kernel.

La UEFI también es un firmware de arranque. Reside en una memoria flash NVRAM integrada en la placa base. Pero es diferente a la BIOS en varios aspectos clave.

1) los ajustes de UEFI almacenados en NVRAM indican la localización de las aplicaciones EFI, que se ejecutan automáticamente al arrancar o se lanzan desde el menú de arranque.
2) Las aplicaciones EFI pueden ser bootloaders, herramientas de diagnóstico, selectores de sistemas operativos...
3) Las aplicaciones EFI pueden estar en cualquier partición que tenga un filesystem compatible (FAT12, FAT16, FAT32, ISO-9660)
4) La partición que contiene las aplicaciones EFI se llama partición ESP (EFI System Partition). *No debe compartirse con otros sistemas de ficheros*

O sea, con la UEFI no estamos limitados al MBR y se pueden usar herramientas mucho más sofisticadas que con la BIOS.

Al arrancar un ordenador con UEFI:

1) La UEFI ejecuta el POST
2) La UEFI activa el monitor, el teclado y el disco de arranque
3) La UEFI lee el contenido de la NVRAM y ejecuta la aplicación EFI predefinida
4) Si la aplicación EFI predefinida es un bootloader se carga el kernel

Además UEFI soporta Secure Boot que solo permite la ejecución de aplicaciones EFI firmadas por el fabricante del hardware.

### The Bootloader

El más popular hoy en día es GRUB. Desde el menú de GRUB podemos elegir cual de los kernels instalados vamos a arrancar y pasarle parámetros.
Algunos de los parámetros más útiles son:

- `acpi`(`on`, `off`)
- `ro`, `rw` (para montar la partición raíz)
- `mem`, `maxcpus` (útiles para máquinas virtuales)
- `root` (para asignar la partición raíz)
- `rootflags` (opciones para montar la partición raíz)
- `init`, `systemd.unit`
- `vga=ask`

### System Initialization

Los pasos para inicializar el sistema operativo son:

- el bootloader carga el kernel en RAM
- el kernel toma el control de la CPU, y empieza a detectar y ajustar aspectos fundamentales como la configuración del hardware y el direccionamiento de memoria
- el kernel accede al initramfs (un archivo que contiene un filesystem que se usa temporalmente como root filesystem durante el arranque)
- cuando el root filesystem está disponible el kernel monta todos los filesystems configurados en `/etc/fstab`
- el kernel ejecuta el primer programa, una utilidad llamad `init`, que es responsable de ejecutar los scripts de incialización y los servicios del sistema

Incluso dentro de una única distribución de Linux existe una gran variedad de maneras de gestionar los scripts de inicialización y los servicios. Cualquier herramienta que los administradores del sistema elijan para gestionar la inicialización del sistema es capaz, como mínimo, de iniciar, detener y reiniciar los servicios del sistema. Estas acciones las puede llevar a cabo el sistema de forma automática (por ejemplo después de un upgrade), pero el administrador del sistema también las necesita (por ejemplo, si se modifica el fichero de configuración de un servicio es casi seguro que hay que reiniciar dicho servicio).

Hay tres herramientas principales:

- SysV
- systemd
- Upstart

### Initialization Inspection

Si hay errores durante el proceso de arranque pueden ser críticos (impedir el arranque) o no (pueden alterar el comportamiento esperado del sistema). En
cualquier caso quedan registrados para que se puedan utilizar en futuras investigaciones. Incluso si no hay errores, la información del proceso de arranque es valiosa para afinar el funcionamiento.

El kernel almacena los mensajes que genera, incluídos los de arranque en un espacio de memoria llamado **kernel ring buffer**. Estos mensajes se pierden al apagar el sistema. El comando `dmesg` (display messages) muestra los mensajes que actualmente contiene el kernel ring buffer. `dmesg --clear` vacía el kernel ring buffer.

En sistemas basados en systemd el commando `journalctl` también muestra el contenido del kernel ring buffer si usamos las opciones `-b, --boot, -k, --dmesg`.
Estos sistemas conservan los logs de todas las inicializaciones (la actual y las anteriores). Podemos ver cuantas inicializaciones conserva con `journalctl --list-boots`.

Todos los mensajes generados por el kernel se almacenan en `/var/log`. Si ocurre un error crítico durante la inicialización y el arranque no va más allá de la carga del initramfs, podemos utilizar un medio de arranque alternativo (por ejemplo, un pendrive con systemrescue), acceder al filesystem y buscar el problema en `/var/log` (usando `journalctl --directory` si es necesario). Los mensajes de systemd no se almacenan en texto plano, así que el uso de `journalctl` es obligatorio.
